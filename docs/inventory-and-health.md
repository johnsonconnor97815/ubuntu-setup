# 机器信息与稳定性检查

状态：完整采集与检查设计草案。阶段顺序以 [已确定的工作流](workflow.md) 为准；其中已实现并只读实测的范围见 [只读原型](prototype.md)，其余检查仍待实现和验证。

当前原型先在 Ubuntu 24.04 / x86_64 开发环境验证信息采集。完整维护功能的支持范围仍待确定。以下将公共检查和按用途启用的检查分开；服务器、虚拟机、容器或 WSL 的实机适配不能由模拟检查代替。

## 先区分三类信息

| 信息 | 例子 | 能用于什么判断 |
| --- | --- | --- |
| 机器实况 | 本次读到的系统版本、设备、软件版本和服务状态 | 判断当前有哪些组件，发现相对上次的变化 |
| 检查结论 | 某设备的所需功能通过验证，或某依赖关系尚未确认 | 判断具体任务能否继续；必须引用对应实况和证据 |
| 用户目标 | 需要中文输入、保留指定版本、用于某类开发 | 决定检查范围、选择方案及判断现状是否满足需求 |

这三类记录分别保存。已安装不等于可用；未采集到不等于不存在；用户目标也不等于机器现状。

## 机器身份与环境

为每个已确认的目标分配本地随机编号。主机名、IP 地址和某个硬件型号都不能单独作为身份依据；更换显卡不应直接产生另一台机器的档案。

记录系统安装实例和运行环境的必要识别信息，以发现档案复制、系统重装或连到其他机器等情况。身份矛盾时先暂停写入，不自动继承旧任务、备份或授权。关联方式和最小识别字段在采集实现前确定，默认不导出原始设备序列号。

真实主机、虚拟机、容器与 WSL 要分别识别。来宾环境看到的设备、内核或模块结果，只能用于该环境能证实的范围，不能当成宿主机验证。

## 采集清单

| 范围 | 需要记录的内容 | 采集时点与限制 |
| --- | --- | --- |
| 系统与会话 | 发行版、版本、架构、运行环境、启动标识；涉及配置时读取桌面、显示协议、会话用户和 Shell | 每次启动复查。启动标识用于发现已经重启，不代替重启后的功能检查 |
| 计算资源 | 处理器型号、架构、内存容量及本次用途需要的能力 | 每次启动复查，硬件变化后重新判断软件要求；容量检查不代表长期负载验证 |
| 存储与基础条件 | 相关路径可写情况、可用空间、安装和恢复需要的存储条件 | 初次检查及写入前复查；空间要求根据具体计划估算，未知时不能编造统一阈值 |
| 软件管理 | 本机使用的安装方式、软件源、包状态、相关版本和依赖、安装是否进行中、元数据更新时间 | 每次启动枚举可识别的安装来源，发现新增、移除和版本变化，再深入检查相关依赖；预览不刷新目标的软件包索引 |
| 其他软件 | 相关的独立安装程序、用户级运行环境、手动安装目录 | 明确已覆盖的来源和目录；不递归扫描所有用户文件，不声称发现了所有手动安装软件 |
| 内核 | 当前运行版本、已安装版本、计划重启后使用的版本及其依据 | 启动、内核变化、驱动计划执行前复查；无法确认下一次启动版本时记为未知 |
| 硬件 | 与用途相关的设备类型、型号、连接或出现状态、系统识别结果 | 启动及设备变化时复查；连接位置变化不必然表示设备更换 |
| 驱动与固件 | 设备和驱动的对应关系、模块版本与加载情况、相关用户态组件、设备功能结果 | 驱动、内核、设备或相关库变化后复查；固件是设备自身运行的软件 |
| 模块加载条件 | Secure Boot 状态、签名和 DKMS 状态等适用信息 | Secure Boot 是启动时的签名检查机制；DKMS 用于为内核构建外部模块。只在相应驱动方案适用时检查 |
| 配置与服务 | 本次用途涉及的配置位置、加载顺序、有效配置、必要服务的状态与近期相关错误 | 按用途和计划读取；不把任意服务失败都视为全机故障，不收集完整无关日志 |
| 已有功能 | 需要保留的关键功能及其可重复检查方法 | 首次建立验证方法，相关变更前后复查；无法自动检测的记录人工验证要求 |

初次采集尽可能完整，后续先复查系统、软件来源、软件清单和硬件概况，再按关键状态和检测到的变化决定深入检查范围。对尚未识别的软件来源标明覆盖缺口，不能只检查已有任务中的软件就声称发现了全部外部变化。每个采集结果独立记录时间；一项刷新成功不能使整份旧档案看起来都已刷新。

只读阶段不为探测而安装工具。现有工具不足、权限不足、超时或输出无法解析时，记录原因和未知范围；如需补充探测依赖，将其列为单独的已授权变更，并重新检查兼容性。

## 每条采集结果的最小字段

字段名称为建议，具体格式见 [数据保存与任务执行](storage-and-execution.md)。

| 字段 | 含义 |
| --- | --- |
| `observation_id` / `machine_id` | 本次观察的编号、所属机器 |
| `scope` / `subject` | 读取的是哪个范围、哪个对象，如某软件或某设备 |
| `observed_at` / `collector_version` | 读取时间、采集逻辑版本 |
| `status` | `observed`：取得有效结果；`unknown`：本次无法确定；`not_applicable`：有依据确认不适用 |
| `value` / `reason` | 取得的值，或无法取得、不适用的具体原因 |
| `coverage` | 本次实际检查的来源、目录、用户或设备范围 |
| `evidence_refs` | 经脱敏的必要结果或其受保护存放位置 |
| `last_known_ref` | 可选，指向上次已知结果；仅供追溯，不能替代本次未知值 |

有效完成设备枚举但未看到旧设备，属于“本次未检测到”；采集失败属于“未知”。要判断设备移除，必须进一步核实。软件也只有在相应来源成功枚举后，才可以判断它是否还存在于该来源。

## 检查结果与依据

每项检查应明确适用条件、输入实况、通过条件、所需证据、影响的任务及重新检查的触发条件。

| 字段 | 含义 |
| --- | --- |
| `check_id` / `rule_version` | 检查项与判断规则版本 |
| `scope` / `required_by` | 检查哪个功能，以及哪些任务需要它 |
| `observation_refs` / `evidence_refs` | 使用了哪些实况、支持信息和验证结果 |
| `checked_at` | 本次核对时间 |
| `result` | `passed`、`failed`、`unknown`、`pending`、`not_applicable` |
| `reason` / `wait_reason` | 结果依据；待验证时说明等待重启、用户操作或其他条件 |
| `validity` / `invalidated_by` | `current` 或 `stale`，以及使旧结果失效的变化 |

`passed` 表示所列通过条件已被验证；`failed` 表示有证据未通过；`unknown` 表示无法判断；`pending` 表示已知还需重启、用户操作等条件才能完成验证；`not_applicable` 必须有不适用的依据。`current` 只表示这条结果仍适用于当前条件，不表示它一定通过。

官方支持信息、包管理器依赖解析和本机功能验证分别保存。官方说明记录来源、对应版本、适用范围和核对时间；元数据还需记录缓存时间与可用性。

有依据支持但尚未本机验证，可以在满足执行条件后尝试变更；已知不兼容或缺少关键依据时，暂停受影响的变更。检查失败会产生修复需求，不要求修复目标在修复前就通过最终验收。

## 拟议检查项目

| 检查项 | 适用条件 | 通过条件 | 未通过时的处理范围 |
| --- | --- | --- | --- |
| 目标与基本信息 | 所有任务 | 能确定目标与相关系统环境 | 目标不明确时暂停写入 |
| 软件包管理可用性 | 依赖该安装方式的操作 | 无妨碍本次操作的未完成事务或未解决依赖问题，所需来源与候选包可核实 | 暂停相关安装；有依据的修复任务可以执行 |
| 空间与写入条件 | 安装、更新、备份或配置写入 | 涉及路径可用，空间满足本次计划及恢复需求 | 暂停相关写入，不自动删除用户文件 |
| 必要更新 | 来源及适用信息可核对时 | 所需安全更新和兼容性修复已评估，必须完成的处理已验证 | 按具体更新影响处理；来源未知时不能报告“已经是安全状态” |
| 设备与驱动 | 该用途需要相关设备 | 型号、运行内核、驱动、相关组件相容，加载与设备功能验证通过 | 暂停依赖该设备的任务；其他任务按依赖继续 |
| 下一次启动所需组件 | 计划切换内核、驱动或存在待重启变更 | 计划内核和所需模块的支持、构建、签名条件可确认；重启后再验证实际加载和功能 | 保留待重启验证，不能用当前内核结果代替 |
| 网络与来源访问 | 需要联网的目标或下载操作 | 当前任务需要的连接可用，来源身份与访问结果可核对 | 暂停相关联网任务；离线可完成的检查继续 |
| 图形会话与显示 | 桌面用途 | 相关显示功能按本机所需方式验证通过 | 暂停相关桌面或显示任务 |
| 音频、摄像头等设备 | 用户用途需要时 | 所需输入或输出功能通过自动检查或用户实际验证 | 暂停相关任务；未使用的设备可列为可选项 |
| 电源与休眠 | 笔记本或用户要求时 | 相关功能有本机验证证据 | 缺少证据时待验证；主动休眠等中断操作须在授权范围内 |
| 关键服务与已有用途 | 用户指定、已选择的能力或本次变更涉及 | 服务及目标功能验证通过 | 暂停依赖任务；报告已有功能是否受到影响 |

检查结果不能自动推出所有硬件、长期负载或未测试场景都稳定。对无法自动完成的验证保留具体待办，不能用用户没有报告问题替代验证通过。

## 进入后续任务的判断

对每个任务分别判断：目标可确定、适用条件有依据、系统基础条件满足、必要前置功能通过、兼容性依据充分、授权覆盖、所引用结果仍有效。

基础性故障可能阻止所有相关写入；功能局部的问题只阻止依赖它的任务。可选检查不能默认为必要检查，也不能把必要检查降成可选来继续执行。

结果失效的触发条件至少包括：相关软件、配置、来源、内核、硬件变化，用户用途改变，检查规则改变，或依据超过该规则允许的有效期。无法判断影响范围时，先补充检查。时间未过期也不能抵消已知环境变化。

## 设计验收场景

以下是完整实现应满足的预期行为。原型已用模拟数据验证其中的信息采集与比较分支；不代表后续执行、恢复或真实设备功能已经验证，实际范围见 [验证记录](prototype.md)。

| 场景 | 预期行为 |
| --- | --- |
| 第二次运行，相关状态未变且功能仍可验证 | 更新实况和检查结果，不重复写入 |
| 用户在 Agent 外升级软件或修改配置 | 记录变化，使相关结论失效，保留外部修改并重新规划 |
| 普通应用变化 | 检查相关目标与依赖，不无依据地重做全部驱动验证 |
| 显卡更换或内核更新 | 重新核对相关驱动和依赖该设备的软件，区分运行与待启动环境 |
| USB 设备临时拔出，或采集权限不足 | 分别记录未检测到或未知，不直接卸载驱动 |
| 缺少适用信息、来源过期或依赖冲突 | 暂停受影响变更，继续可独立完成的检查 |
| 容器里能看到部分硬件信息 | 记录来宾环境限制，不将结果作为宿主机功能验证 |
| 新需求改变已有驱动要求 | 重新评估受影响计划，不直接沿用已完成阶段的结论 |
