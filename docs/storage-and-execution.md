# 数据保存与任务执行

状态：完整存储与执行设计草案。只读原型已使用本地 JSON、JSONL 和单写入任务，实际路径与格式见 [只读原型](prototype.md)。本文件中的变更计划、系统操作状态和恢复资料结构仍待实现；多用户共同管理同一目标、远程控制及数据库方案尚未确定。

共同的流程约束见 [工作流](workflow.md)，观察和检查结果的含义见 [机器信息与稳定性检查](inventory-and-health.md)。本文件维护存储与任务状态的定义。

## 保存方式

JSON 是结构化文本，适合保存目标、计划和检查结果；JSONL 每行是一条 JSON 记录，适合逐条追加操作事件。面向用户的报告统一使用 HTML，从任务记录生成，完整保存后默认请求浏览器打开；原有 Markdown 历史记录保留，兼容规则见 [HTML 报告](html-reports.md)。

建议遵循用户设置的 `XDG_CONFIG_HOME`、`XDG_STATE_HOME`、`XDG_CACHE_HOME` 存放配置、状态和缓存。未设置时，拟用以下目录：

```text
~/.config/ubuntu-setup/
  preferences.json
  targets/<machine-id>/goals.json

~/.local/state/ubuntu-setup/
  targets/<machine-id>/
    identity.json
    inventory/current.json
    inventory/snapshots/<snapshot-id>.json
    assessments/<assessment-id>.json
    runs/<run-id>/
      request.json
      decisions.jsonl
      plans/<revision>.json
      events.jsonl
      state.json
      report.html
      artifacts/
      backups/

~/.cache/ubuntu-setup/
  evidence/<cache-entry-id>/
```

以上是完整产品的目录建议。原型只创建检查需要的状态子集，具体差异见 [只读原型](prototype.md)。机器档案、目标清单、日志和备份保存在仓库之外；仓库只保存公共流程、检查定义、能力说明和不含真实机器信息的测试数据。

`backups/` 仅保存权限适合当前管理用户的备份。需要管理员保护的配置，拟保存在目标机 `/var/lib/ubuntu-setup/private-backups/` 下的受保护目录；普通任务记录只保存引用。创建这种目录属于实际执行，预览不创建。

## 记录关系

| 记录 | 保存内容 | 更新规则 |
| --- | --- | --- |
| 用户偏好与目标 | 用途、版本要求、必须保留的功能、所选通用能力、用户明确排除的项目 | 修改时保留版本；每次任务保存当时的目标副本。目标和偏好不自动构成授权 |
| 机器身份 | 本地编号、已确认的目标关联及识别依据 | 身份矛盾时停止关联旧任务，先核实目标 |
| 观察快照 | 分范围的采集结果、时间、覆盖范围及必要证据 | 新快照不覆盖旧快照；`current.json` 只作为最近观察的索引 |
| 检查结果 | 规则版本、输入、依据、结果、有效性及影响的任务 | 复查产生新结果，旧结果保留；变化使相关旧结果失效 |
| 请求与决定 | 本次需求、目标版本、明确选择、授权范围及可核对的来源 | 按任务保存；新增选择追加记录，不能靠改写文件制造用户授权 |
| 计划 | 与具体目标和实况对应的操作、依赖、连带影响、验证及恢复方式 | 每次变化生成新版本，不覆盖已执行版本 |
| 操作事件 | 哪个步骤开始、完成、失败、等待，以及必要的结果引用 | 按顺序追加，保留执行尝试与计划版本 |
| 当前任务状态 | 各操作的当前状态和已处理的事件序号 | 可由已保存事件重建，不能单独作为命令成功的证据 |
| 报告 | 已验证完成、跳过、失败、待处理和恢复资料位置 | 根据记录生成；报告中的“完成”必须有验证依据 |
| 外部依据缓存 | 来源、对应版本、获取和核对时间、适用范围、必要摘要 | 可重新获取；被计划引用的重要依据另存任务资料，不能因缓存清理丢失 |

当前观察必须反映本次检测失败或未知的范围，不能静默填入旧值。可以引用上次已知结果供排查，但其原始时间和有效性必须保留。

## 公共字段

每类结构化记录有 `schema_version`，表示记录格式版本。目标相关记录有 `machine_id`；运行相关记录再带 `run_id`。各记录有独立编号及带时区的时间，序列顺序另由事件序号确定，不依赖机器时钟永远准确。

实现时需要能识别旧格式，并在必要迁移前保留原文件。不认识的格式不能按空档案处理后重新初始化系统。

以下是合成的观察示例，用于说明“本次未知”和“上次已知”如何区分，未采集任何真实机器信息：

```json
{
  "schema_version": 1,
  "observation_id": "example-observation-new",
  "machine_id": "example-machine",
  "scope": "driver",
  "subject": "example-display-device",
  "observed_at": "2026-09-17T00:00:00Z",
  "collector_version": "example-only",
  "status": "unknown",
  "value": null,
  "reason": "本次检测权限不足",
  "coverage": ["example-display-device"],
  "evidence_refs": [],
  "last_known_ref": "example-observation-old"
}
```

## 计划最小内容

| 内容 | 要保存的字段或信息 |
| --- | --- |
| 计划身份 | 计划编号、`revision`、目标机器、请求、目标版本、创建时间 |
| 所用条件 | 观察和检查结果引用、规则版本、来源依据及其时间、仍待核实的内容 |
| 操作目的 | 对应能力或修复目标、所属阶段、为什么需要执行 |
| 实际影响 | 软件及依赖的安装、升级、降级和移除清单；配置差异；驱动和相关组件变化 |
| 依赖与分组 | 操作前必须满足的条件、依赖的任务、必须配套生效的操作组和执行顺序 |
| 执行要求 | 精确目标版本或配置、权限、服务中断、重启要求、对应的授权范围 |
| 验证与恢复 | 目标和受影响已有功能的检查方法、所需备份、恢复步骤及其限制 |
| 执行前复核 | 哪些当前值必须重新读取、何时需要重新解析依赖、哪些差异使计划失效 |

预览中使用的旧元数据不能自动变成执行依据。执行前按授权范围补充必要数据、重新解析依赖；结果与计划不同时生成新版本，重新检查兼容性和授权范围，再执行受影响步骤。

已执行事件继续引用原计划版本。尚未执行的操作只能采用当前有效计划。已经发生的变更不会因计划被替换而从记录中消失。

## 操作状态

状态用于描述一项操作的进度，与机器健康状况分开。

| 状态 | 含义 | 可以如何继续 |
| --- | --- | --- |
| `planned` | 已列入计划，执行条件尚未全部核对 | 补充前置检查，进入 `ready` 或 `waiting` |
| `ready` | 兼容性、依赖、目标条件和授权已核对 | 开始前再次检查相关状态；符合条件才进入 `running` |
| `running` | 已记录开始，操作正在执行 | 根据实际结果进入 `verifying`、`waiting` 或 `failed` |
| `verifying` | 正在验证目标功能及受影响功能 | 进入 `succeeded`、`waiting` 或 `failed` |
| `waiting` | 等待明确条件 | 保存 `wait_reason` 和相关对象；条件改变后重新检查，不直接重发命令 |
| `succeeded` | 所需验证已通过 | 记录是否实际写入；环境变化后另建复查或新尝试，保留历史结果 |
| `failed` | 执行或验证失败 | 保留证据；按恢复方案处理，有新依据时建立新的尝试 |
| `skipped` | 有依据不适用，或用户明确未选择、跳过 | 必须说明原因；必要前置条件不能靠跳过变成通过 |
| `interrupted` | 无法确定上次执行是否结束或实际结果是什么 | 读取现场和记录，决定继续验证、恢复或重新规划 |

`waiting` 的原因包括依赖未满足、关键依据不足、等待用户决定、等待授权、等待重启、等待人工验证、相关资源正在被其他任务使用。报告需显示具体原因和下一步，不能只显示“等待中”。

已满足目标且本次验证通过的操作可记为 `succeeded`、`changed=false`，向用户说明“已满足，跳过写入”。安装成功但待重启时记为 `waiting`，不得提前记为 `succeeded`。

等待条件解除后先读取现场。如果写入已完成且前置条件仍满足，进入 `verifying`；如果还需要变更，回到 `planned` 重新核对计划后再执行。用户要求暂停时，在当前操作可以安全结束的位置停止后续写入，保存等待原因和已发生的变更；收到继续请求后同样先复查现场。

每条操作事件至少包含事件序号、事件编号、机器与运行编号、计划版本、操作编号、尝试编号、时间、事件类型和结果引用。重新尝试使用新的尝试编号，不覆盖先前失败或中断的记录。

## 一次执行与中断恢复

1. 确认目标、计划版本及授权来源，防止多个本项目任务同时修改同一目标。软件包管理器等已有锁也必须遵守，不强制删除。
2. 重读操作的必要前置条件；有变化时先更新观察、使受影响计划失效并重新规划。
3. 确认恢复资料可用，保存变更前内容、权限和属主。记录操作开始并确认必要记录已持久保存，之后才启动系统变更。
4. 保存命令结果或操作结果，检查实际变化，记录失败和部分完成情况。
5. 验证目标与受影响功能，更新检查结果、操作事件和当前状态。必须配套生效的操作组需要整组验证才能放行依赖任务。
6. 恢复运行时，先确认是否仍有原操作在进行；无法确定时保留等待或中断状态，不重复启动同一操作。操作已结束但结果缺失时，根据现场决定是否继续验证。

本项目的任务锁不能阻止所有外部修改。操作前后需要重新核对相关状态；发现变化后按 [工作流](workflow.md) 处理。恢复配置前检查当前内容，存在外部修改时保留差异并重新制定恢复步骤。

写入单个 JSON 文件时，先写完整临时文件并持久保存，再替换当前文件，避免只留下半份状态。JSONL 事件带递增序号；中断留下的不完整末行保留供排查，不当作完成事件。中间记录损坏或状态与事件不一致时保留原资料，重新核对现场，不能静默宣告成功。

操作组记录已完成的子步骤和整组结果。部分失败时停止依赖整组结果的任务，按恢复方案处理；恢复本身也要验证，不能承诺所有软件或驱动变更都可自动撤销。

## 数据保护与保留

记录仅包含判断任务需要的信息，不保存密码、令牌、完整环境变量或无关用户数据。命令参数、输出、配置差异和网址也需要检查是否含秘密。

本地状态目录建议仅管理用户可访问。备份不得降低原配置的保护要求；受管理员保护的备份保留在目标机受保护位置，普通报告不展开敏感内容。访问恢复资料失败会阻止依赖该恢复方案的写入。

首版建议暂不自动删除任务记录和恢复资料。缓存可以重新获取；清理记录、备份、导出和磁盘占用控制的具体策略待确定。复制目标清单到另一台机器时，只迁移用户意图，不继承旧机器实况、兼容性结论、执行进度或授权。

## 设计验收场景

以下为完整执行流程的预期行为。原型已经验证只读记录的中断、损坏和并发处理；安装、重启及配置恢复情形仍未实现，不能把只读测试算作系统变更验证。

| 场景 | 预期行为 |
| --- | --- |
| 依赖重新解析后新增移除项 | 形成新计划，重新判断影响与授权；不沿用旧清单直接执行 |
| 记录开始后中断，实际安装已完成 | 核对版本和功能后继续验证，不仅凭缺少完成事件重装 |
| 原安装仍在运行 | 等待或报告状态，避免启动第二个同类操作 |
| 配置候选内容校验失败 | 保留原配置，操作失败或等待修订方案 |
| 命令成功但功能验证失败 | 记录失败，暂停依赖步骤，按恢复方案处理 |
| 重启后启动了非计划内核 | 重新检查实况和驱动，不自动将等待任务记为成功 |
| 恢复前发现用户新改动 | 保留当前内容和差异，重新规划恢复，禁止旧备份直接覆盖 |
| 两个 Agent 工具同时操作同一目标 | 仅一个执行任务写入，另一个等待或只读查看；具体跨进程机制在实现时验证 |
| 文件损坏或格式不认识 | 保留原数据，暂停依赖这些记录的变更，不当成首次初始化 |
