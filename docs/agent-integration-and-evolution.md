# Agent 接入与能力改进

状态：开发应遵守的设计约定。`0.2.0` 已提供 Python 命令行程序、JSON 报告、独立检测规则和能力目录；独立离线检测入口、专用 Agent 接入及自动改进流程尚未实现。当前可用范围以 [只读原型](prototype.md) 和 [检测规则](detection-rules.md) 为准。

本文补充 [工作流](workflow.md)，不改变系统与驱动维护优先的顺序。兼容性、权限、恢复及验证规则仍统一维护在 [AGENTS.md](../AGENTS.md)。

## 当前如何获取信息

Agent 通过本地命令执行工具调用：

```sh
python3 -m ubuntu_setup inspect --format json
```

这是 Python 实现的命令行程序。主程序使用标准库，部分扩展检查通过受控子进程调用已有的系统组件。具体采集方法写在程序里：读取系统文件或使用固定命令入口，变量参数先验证，再解析并保存结果。它不调用语言模型，也不会每次临时生成一套采集脚本。`0.7.0` 的联网检查、设备反馈记录和环境变化处理见 [扩展检查](extended-checks.md)。

| 当前文件 | 职责 |
| --- | --- |
| [cli.py](../ubuntu_setup/cli.py) | 接收参数，串起采集、比较、有限检查和保存 |
| [collect.py](../ubuntu_setup/collect.py) | 只读查询系统、软件、硬件、驱动等信息 |
| [analysis.py](../ubuntu_setup/analysis.py) | 比较变化，安排已有的有限检查，标出失效结论 |
| [rules.py](../ubuntu_setup/rules.py) | 独立规则、能力说明、规则版本与证据引用 |
| [state.py](../ubuntu_setup/state.py) | 保存私有机器档案、运行记录，处理并发与中断 |
| [report.py](../ubuntu_setup/report.py) | 生成 HTML 用户报告、终端摘要和 JSON 输出；HTML 样式与交互维护在模板中 |
| [browser.py](../ubuntu_setup/browser.py) | 完整保存后请求桌面打开报告，失败时保留文件与路径 |

当前 `inspect` 一次完成这些步骤。采集范围和规则以受版本管理的 Python 代码维护，各规则有独立版本，可通过 `capabilities` 查询用途、输入和限制。JSON 是便于程序读取的结构化文本，已有输出并不等于已经完成专用 Agent 接入。

退出码 `0` 只表示报告保存完成。Agent 必须读取具体检查结果、依据和未知项，不能据此宣布系统稳定。当前异常退出主要通过退出码及标准错误文本报告；统一的结构化错误格式也尚未实现。

## 接入时的分工

采用公共程序加薄接入层。接入层只负责把宿主 Agent 的调用转换成公共程序的输入，并把结果交还给它。

| 部分 | 负责什么 | 怎样复用 |
| --- | --- | --- |
| Agent | 理解用途、选择检查、查证资料、分析原因、安排任务、向用户解释 | 读取同一份公共流程和能力说明；推测与已证实结论分开 |
| 工作说明 | 说明何时调用什么能力、怎样解释结果、失败后如何继续 | 公共内容只维护一份；宿主入口引用它 |
| 公共程序 | 采集、按明确规则判断、校验计划、执行已授权操作和验证 | Python 核心保持与宿主无关；目前只实现前面的采集与有限检查 |
| 本地记录 | 保存实况、依据、任务进度及能力版本 | 作为可追溯记录；换会话后重新核对现场，不能只凭聊天摘要继续 |

Skill 是供 Agent 按需读取的工作说明，可附带脚本和参考资料。OpenAI 官方文档支持把固定步骤交给脚本，把需要结合上下文的判断交给模型，并让工作说明按需加载。[1][2]

第一版接入优先复用现有命令行和 JSON；需要封装 Skill 时，入口引用公共说明和程序，不复制采集、检测或修复逻辑。只有出现统一工具调用、远程访问或共享服务的实际需求时，再评估 MCP，即 Agent 连接外部工具和数据的协议。当前不引入独立模型服务、常驻进程或通用插件框架。

Codex 的 Skill 和 `AGENTS.md` 用法已按官方资料核对。Claude Code CLI 及其他工具接入时，分别核实所用版本的入口、命令执行和权限能力，并记录实测结果；不能从“能运行命令”直接推断它们都自动加载相同文件或沿用相同授权。

## 每项能力需要说明什么

能力可以是采集器、检测规则、计划生成、变更执行或功能验证。先以普通 Python 模块和明确的数据定义实现，不需要运行时下载或动态加载任意代码。

以下约定覆盖完整产品；当前检测规则已实现的字段以 [检测规则](detection-rules.md) 为准，执行与恢复部分仍待实现：

| 信息 | 最小约定 |
| --- | --- |
| 身份与版本 | 稳定编号、能力版本、输入与输出格式版本；分别记录采集逻辑、规则和工作说明的版本 |
| 使用时机 | 解决什么问题、何时使用、适用的系统与设备、覆盖范围和已知限制 |
| 输入与前提 | 所需观察、目标和来源证据；目标机器、快照或计划引用；缺失时如何处理 |
| 结果与证据 | 实际结果、原因、时间、所用证据、未确认项和可继续的步骤 |
| 副作用与权限 | 是否只读目标系统，是否写本工具记录，是否联网，是否需要提权或中断服务 |
| 失败处理 | 区分工具缺失、权限不足、超时、格式变化和检查未通过；说明有何新条件才值得重试 |
| 重新判断条件 | 哪些软件、配置、硬件、用途、来源或规则变化会使结果失效 |
| 验证与恢复 | 怎样验证能力本身和目标功能；执行能力还需列出备份与恢复限制 |

程序负责校验输入、格式和必要条件，工作说明不能代替这些检查。执行入口应接收有具体目标和版本的计划引用，重新核对现场与可验证的授权来源；不能以任意命令字符串或自行填写的 `approved: true` 代替计划和授权。

结构化结果区分“调用是否完成”与“目标检查是否通过”。检查继续使用 `passed`、`failed`、`unknown`、`pending`、`not_applicable` 的既有含义；信息缺失不能转成通过，也不能因调用失败而误报系统故障。

面向 Agent 默认给摘要、问题和证据引用，需要时再读取具体软件或设备的记录，避免把整份清单反复放进对话。能力查询与证据路径已提供，按范围读取记录的专用接口和命令级结构化错误仍待补充；引入新格式时保留版本兼容或明确迁移方式，不能静默改变已有 JSON 含义。

系统输出、日志、软件描述和外部网页作为待核实的数据处理。其中出现的操作指令不能自动成为项目规则、用户授权或可执行计划。

## 下一步检测怎样实现

保持已定次序：获取信息 → 按规则检测 → 分析异常原因 → 制定维护计划 → 执行并验证。

首版独立检测规则已实现，后续继续扩展检测能力。规则读取有时间、范围和版本的观察；缺少信息时提出具体的补充采集需求，由采集器完成。检测过程中不顺带安装依赖、修复配置或重启。

每条规则独立声明所需观察、适用条件、通过条件及失效条件。已有固定检查已拆成可单独验证的规则，并增加 DKMS 安装记录判断；后续补充更多有依据的系统基础检测。`inspect` 继续作为一键入口，避免让用户手动串起每个内部步骤；是否增加其他命令，在对应能力实现时确定。

异常原因需要另行查证。例如“发现失败服务”是观察，“它影响哪个用途”需要对应规则，“驱动版本造成失败”则需要诊断证据。这些结论不能合并为一个未经验证的修复决定。

至少覆盖信息缺失、部分失败、已满足条件、不适用环境、等待重启和环境变化后重查。用同一批合成输入验证命令行与接入层给出的结果一致。安装、驱动功能和重启验证继续使用符合要求的测试环境。

## 自进化具体改进什么

这里的自进化指：Agent 从失败、未知结果和用户纠正中发现能力缺口，形成可重复验证的改进，再按版本采用。它不依赖训练底层模型，也不以增加聊天记忆代替程序验证。

| 改进对象 | 例子 | 生效条件 |
| --- | --- | --- |
| 采集与解析 | 工具输出格式变化，原有解析失败 | 有复现输入、预期结果及旧格式测试，覆盖受影响环境 |
| 检测与兼容规则 | 发现漏检、误报，或官方支持范围更新 | 证据能支持规则，明确适用范围，正常与异常案例均经过验证 |
| 工作说明与交互 | Agent 反复选错工具，或将未知结果说成通过 | 用相应任务案例检查工具选择、参数和解释结果；只修改相关说明 |
| 计划、执行与验证方法 | 新方案可减少失败，或原验证漏掉已有功能损坏 | 在隔离环境验证变更、重复执行、中断与恢复；硬件结论另需适合的实机证据 |

机器档案更新只说明机器变了；能力改进才说明程序或工作方法变了。单台机器上的经验先保留它的适用条件，不能直接推广到所有 Ubuntu 版本、内核或硬件。

## 改进如何验证和采用

1. **记录问题。** 保存受影响能力及版本、预期与实际结果、必要证据、复现条件和用户纠正。未知结果只是调查线索，不自动说明程序存在缺陷。
2. **建立案例。** 将必要信息整理为合成或脱敏输入，明确正确结果。正确结果应来自可核对的资料、功能验证或明确需求，不能只照抄模型建议或旧程序输出。
3. **形成候选修改。** 在隔离开发副本中修改代码、规则或说明，保留差异、依据和影响范围。正在维护机器的任务继续使用原版本。
4. **比较新旧行为。** 先验证发现问题的案例，再检查受影响的已有案例。涉及 Agent 判断时，评估是否选对工具、参数是否正确、是否诚实表达未知，以及是否遵守任务边界；记录宿主、模型和说明版本中实际可取得的信息。[3]
5. **按证据采用。** 达到事先定义的通过条件后，在已授权的开发或发布范围内采用新版本。通过合成测试只证明相应逻辑；涉及驱动、重启或设备功能的支持结论仍须满足项目的实机验证要求。
6. **记录效果与退回条件。** 保存启用版本、范围和验证结果；新缺陷出现后可停用或退回能力版本，并重新检查受影响的旧结论。程序退回不等于目标系统变更已经撤销。

评估同时保留正常案例、失败案例、边界条件和此前无关的已有能力，避免只针对新案例修改。将未知误判为通过、忽略目标变化或越过授权的候选不得采用。模型可以帮助找问题和写候选修改，不能仅凭自己的评分宣布改进成功。

现有原型已有一个可复用的改进案例：读取 `/proc` 文件时，一次请求过大的读取缓冲区曾触发 `ENOMEM`；改为小块读取后，补充回归测试并在本机只读验证。后续将这种过程留下的证据、案例和版本关联起来，才能让下次遇到同类问题时直接受益。

每次改进应有明确问题、验证目标和尝试范围。没有新证据时记录未解决原因，不无限重复生成或执行同一修改。发布与启用沿用有效授权，只对超出范围的具体新增影响补充决定，不能因为“自进化”给自己增加系统操作权限。

## 改进记录如何保存

沿用 [数据保存与任务执行](storage-and-execution.md) 的原则，先采用本地文件，不增加数据库或外部上传服务。以下记录结构仍待实现：

| 记录 | 保存位置与内容 |
| --- | --- |
| 机器现场与原始证据 | 现有私有机器目录；保留运行、快照和检查引用，不提交仓库 |
| 问题与候选修改记录 | 拟放在私有状态目录的 `improvements/<case-id>/`；保存能力及版本、复现条件、证据引用、候选差异、测试结果和当前状态 |
| 可复用测试与公共依据 | 经检查的合成或脱敏案例随代码保存；公共支持资料记录来源、对应版本、核对时间和适用范围 |
| 能力版本与采用记录 | 公共代码及说明按版本维护；本地运行另记实际采用的版本和适用范围，可追溯到对应案例与验证结果 |

问题记录区分待复现、候选、验证通过、已采用、已撤回和已否决；验证通过与采用是两件事。没有足够依据的问题可以保留待处理，同类问题用同一案例关联后续运行，避免反复创建候选。

每次维护任务固定所用能力版本。新版本在任务边界生效，中断恢复时核对版本与现场；涉及规则变化的旧结论重新评估。涉及存储格式变化时，先验证迁移和旧记录保留方式；不兼容的旧程序不能直接读取新格式或静默重建档案。

真实机器记录默认留在本地。将失败案例提交仓库或用于外部评估前，只提取必要信息并检查脱敏结果。授权和来源不明的经验文本不能作为可跨机器复用的知识。

## 实施顺序与验收

| 次序 | 交付内容 | 怎样确认完成 |
| --- | --- | --- |
| 1 | 已提供首版独立检测规则及能力说明，继续扩展覆盖范围 | 现有 `inspect` 可继续使用；新增规则有依据、证据引用、未知处理与变化重查测试 |
| 2 | 首个 Agent 接入及公共接口约定 | 正确发现并调用能力，读取 JSON，保留失败与未知；记录具体宿主版本的实测结果 |
| 3 | 问题案例、候选修改和版本采用记录 | 完成一次“真实问题 → 脱敏案例 → 修改 → 比较验证 → 采用或否决 → 追溯”的流程 |
| 4 | 在既有验证基础上增加自动化 | 先自动整理问题和运行测试，再在授权范围内自动采用合格改进；测量误判、复发、耗时等实际效果 |

这四步应逐步实现。当前已有结构化记录和合成测试可复用，尚不能声称已经支持自动改进、自动升级或多 Agent 工具适配。
