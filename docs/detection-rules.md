# 检测规则与能力目录

状态：`0.7.0` 已实现。规则只从观察记录作出有限判断，不自行读写系统或联网。采集阶段支持可选的隔离联网核实和有限设备测试，不安装软件或修改目标配置。对外使用 `inspect` 和 `capabilities`；新增 5 项详见 [扩展检查](extended-checks.md)。

## 可用命令

在仓库根目录运行：

```sh
python3 -m ubuntu_setup capabilities --format json
python3 -m ubuntu_setup capabilities --check drivers.dkms.current
python3 -m ubuntu_setup inspect --format json
```

`capabilities` 不采集机器信息、不读取或写入机器档案。它列出操作入口和规则说明；`--check` 按编号查看一条规则，不执行该检查。JSON 输出有独立的 `schema_version: 1`、程序版本、`operations` 和 `checks`。

`inspect` 仍先采集，再执行全部规则并保存报告。退出码 `0` 表示报告完整保存，可能同时有失败、未知或待验证结果。错误退出仍使用退出码和标准错误文本，统一的 JSON 错误响应尚未实现。当前没有独立的离线检测命令。

从 `0.3.0` 起，用户报告采用 HTML，保存后默认请求浏览器打开；自动化调用可使用 `--no-open`。规则判断与证据不变，具体行为见 [HTML 报告](html-reports.md)。

`0.4.0` 增加普通用户说明和可选的 `reason_code` 原因编号。报告按稳定编号选择文案，原结果、技术说明、判断逻辑与规则版本保留；文案版本独立记录，详见 [文案维护](html-reports.md#文案与检测分开维护)。

## 当前覆盖范围

目录共有 13 条记录，全部已经实现所声明范围的检查，其中 3 条仅确认采集方法或读取信息。每条说明和结果保留 `implementation_status`；历史记录中的 `not_implemented` 不会被改写成已完成。

| 编号 | 当前检查内容 | 限制 |
| --- | --- | --- |
| `platform` | 系统、架构和运行环境是否属于首批采集实测组合 | 目前只有 Ubuntu 24.04 / x86_64 真实主机；其他组合为未知，不等于已知不兼容 |
| `environment` | 是否取得明确的运行环境类型 | 不将来宾环境结果当作宿主机状态 |
| `packages.state` | dpkg 登记是否存在未完成安装或异常标志 | 残留配置不算未完成安装；不解析完整依赖 |
| `storage.basic` | 根文件系统是否只读、可用空间是否耗尽 | 不判断具体安装计划所需空间，也不证明目标路径可写 |
| `reboot` | 重启提示及此前的重启等待 | 提示消失但未确认经历重启时保留等待；重启不等于功能通过 |
| `drivers.modules` | 动态模块清单是否取得 | 只检查清单读取，不判断模块兼容或设备功能 |
| `drivers.dkms.current` | DKMS 登记模块与运行内核、架构的安装记录是否匹配 | 见下表；不判断下次启动内核、签名或设备功能 |
| `services` | 当前可见系统单元是否存在失败项 | 单元包括服务及其关联任务；失败原因和用途影响仍需查证 |
| `packages.dependencies` | 当前依赖完整性；候选更新的安装、升级、降级与移除模拟 | 只覆盖 APT/dpkg；应用功能和任意新安装方案另验 |
| `drivers.compatibility` | 已绑定设备标识、运行内核、模块文件、运行与磁盘版本、固件声明、签名存在性；适用时测试 NVIDIA 管理接口 | 不证明签名信任、所有固件选择、下次启动内核或厂商完整支持关系 |
| `hardware.function` | 离屏绘制与像素回读；屏幕、声音、输入的人工使用确认 | 软件绘制不证明 GPU 加速；确认绑定环境，条件变化后失效 |
| `updates` | 本地更新候选和信任绕过设置；可选联网核实来源签名和索引有效期 | 默认缓存结论未知；不检查全部漏洞或支持期限 |
| `configs` | sysctl.d 数字设置与当前值；已加载系统单元配置状态 | 未覆盖的文件和格式保持未知；不自动应用设置 |

失败服务会记为该项检查 `failed` 并列出名称。它不直接证明系统整体不可用，也不会触发自动修复。采集不到服务清单则为 `unknown`，两种情况明确区分。

DKMS 是为不同内核构建和安装外部模块的工具。当前规则按下列范围解释已保存的 `dkms status` 文本：

| 观察 | 结果 |
| --- | --- |
| 无法确定运行环境，或无法取得 DKMS 清单 | `unknown`；工具缺失不等于没有外部驱动 |
| 容器或 WSL；或成功读取的 DKMS 清单为空 | `not_applicable`，并说明原因；不扩大到其他驱动检查 |
| 登记模块都有当前内核和架构的 `installed` 记录 | 此安装记录检查 `passed`，实际驱动功能仍未验证 |
| 当前内核和架构的模块仅为 `built` | 此安装记录检查 `failed`；先核实设备是否需要它，不直接安装 |
| 模块只有 `added`、其他内核或其他架构记录 | `unknown`；可能是旧内核留存，不能直接认定驱动损坏 |
| 出现警告、未知状态、部分无法解析或重复记录 | `unknown`，不丢弃问题行后报告通过 |

解析仅支持 `module/version: added` 和 `module/version, kernel, architecture: built` / `installed` 的完整无附注形式。尚未对真实 DKMS 安装环境实测；其他格式继续保留未知。

## 结果如何追溯

沿用记录格式版本 `1`，保留原有字段和历史证据。程序可继续读取旧档案，不覆盖历史报告。`0.7.0` 新增 5 个 `checks.*` 观察范围；旧快照完整的原范围仍被接受，续接时记为新增采集范围，不伪造历史观察编号或设备移除。

| 位置 | 新字段及用途 |
| --- | --- |
| 每项检查 | `implementation_status`；`evidence_refs` 指向本次快照、观察编号、范围、采集时间、采集版本及覆盖范围；`unavailable_inputs` 列出本次缺失的输入；`basis_refs` 指向规则依据 |
| 每项异常检查 | `subjects` 列出受影响的包、服务或模块；不在摘要里展开整份机器清单 |
| 规则执行失败 | `error.code: rule_error` 与异常类型；结果为未知，不保存可能含敏感信息的异常原文 |
| 检查记录和 JSON 报告 | `rule_versions` 保存本次每条规则的版本；`rule_changes` 列出相对上次的新增、更新和移除 |
| JSON 报告 | `snapshot_id`、`assessment_id`、`snapshot_path`、`assessment_path` 供调用方按需读取具体记录 |

`basis_refs` 中的仓库路径相对仓库根目录，`man:` 指向文档所记录版本的系统手册，网页地址指向外部依据；它们不会自动触发联网或命令执行。

缺失信息仍引用本次未知观察，不借用历史值来放行检查。单条规则执行出错后记录未知，其他独立规则继续；用户中断仍会停止本次运行。档案里的新证据引用与对应快照不一致时拒绝续接，保留原记录。

`validity: current` 沿用原义：结果适用于本次所引用的观察条件，不表示结果通过，也不表示以后永远有效。采集与判断之间并非整机原子操作；执行系统变更前仍需复核现场。

## 规则变化如何处理

规则定义在 [rules.py](../ubuntu_setup/rules.py)，变化比较与整次检测在 [analysis.py](../ubuntu_setup/analysis.py)。每条规则有独立版本、声明输入、适用条件、通过条件、限制及失效范围。一次运行固定采用的规则集合。

规则更新使相关旧结论失效，新增规则产生新结果，移除规则不再产生新结论。版本未变但输入范围发生变化时，也会报告规则变化并使旧结论失效。软件、配置、硬件和启动变化继续触发相关重查；软件到驱动的初步关联只用于提醒复查，不能证明依赖兼容。

采集逻辑版本独立于程序版本：原观察仍使用 `0.1.0`；新增 `checks.*` 范围使用 `0.2.0`。新增功能不会把所有原设备报告为变化。5 项原占位规则升级为 `2`，其他规则版本保持；旧结论按版本和输入范围重新评估。

## 怎样增加或改进规则

1. 明确需要解决的问题，查证判断依据及适用范围，准备正常、异常和信息不足的合成案例。
2. 在 `rules.py` 添加或修改独立判断函数，只通过 `Inputs.value()` 读取声明的观察，返回 `Outcome`；函数不自行采集、联网或修改系统。缺少前提时返回未知，并说明需要补什么。
3. 在 `RULES` 中登记规则说明。`required_scopes` 表示进入判断前必须取得的观察；需要分支判断不适用或保留等待状态的规则，可以在函数内部检查各项前提。函数不能读取未声明范围。
4. 判断条件、支持范围或必要证据改变时更新该规则版本。补充回归案例，比较受影响规则的新旧行为，验证相关旧结论会失效、已有重启等待不会丢失。
5. 更新依据、限制和验证记录，再在已授权开发范围内采用。旧结果保留原版本与证据，不能用新结论改写旧报告。

运行检查：

```sh
python3 -m unittest discover -s tests -v
git diff --check
```

自动测试覆盖规则隔离、未声明输入、未知处理、版本变化、旧档案续接、证据损坏、失败服务和 DKMS 匹配分支，全部使用合成数据或临时文件。实际采集验证范围见 [原型验证记录](prototype.md)。

这些是后续能力改进的基础：规则可定位、可测试、可追溯。自动整理问题、生成候选修改、评估 Agent 工具选择和自动采用新版本仍未实现，完整设计见 [Agent 接入与能力改进](agent-integration-and-evolution.md)。
